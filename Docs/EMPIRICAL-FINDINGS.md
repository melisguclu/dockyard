# Empirical findings

The plan listed twelve assumptions to verify on real hardware before relying on them. This file records what has actually been checked, on what, and what changed as a result.

Verified on: M1 MacBook Pro, macOS 26.5.2 (build 25F84), built-in Retina display plus Apple Studio Display, Dock on the Studio Display, `tilesize` 27, `largesize` 48, magnification on, auto-hide off.

| # | Question | Status | Finding |
|---|---|---|---|
| Q1 | Does `com.apple.dock.prefchanged` fire for every mutation path? | Partly verified | Fires for Dock-initiated changes. The directory watcher on `~/Library/Preferences` is kept as a backstop and is cheap, because the store diffs before publishing, so a spurious wake-up costs one domain read and no UI work. |
| Q2 | Does `CFPreferencesAppSynchronize` invalidate another app's cached domain? | Verified | Yes. Values written externally are visible on the next read after synchronizing. |
| Q3 | Which `NSVisualEffectView` material matches the Dock? | Partly verified | `.hudWindow` with `.behindWindow` blending is the closest public material on both Sonoma-era and Tahoe. Tahoe's Liquid Glass has no public equivalent, so a visible difference remains. The material is a single constant in `DockMaterial`. |
| Q4 | Exact inter-tile spacing and edge margin as a function of `tilesize` | Changed the design | The edge margin no longer needs fitting: the display hosting the real Dock reserves a strip equal to `barThickness + margin`, readable as the `frame` minus `visibleFrame` inset, and Dockyard uses that measurement directly. Measured 47 points at `tilesize` 27, where a ratio-only constant gave 40. Spacing and padding remain screenshot-derived; see `GEOMETRY.md`. |
| Q5 | The precise magnification falloff curve | Modelled, not yet fitted to screenshots | Raised-cosine over a ±3 tile window, with outward displacement anchored at the cursor. Unit tests pin the invariants: peak at the cursor, unity at the window edge, monotone, symmetric, total width equal to the sum of scaled widths, no gaps or overlaps, clamped at both display edges. |
| Q6 | Does a dock-level non-activating panel float correctly over full-screen apps? | Not yet verified | Release-checklist item. `.fullScreenAuxiliary` and `.canJoinAllSpaces` are set. |
| Q7 | Does `CGDirectDisplayID` change across a Studio Display disconnect and reconnect? | Not yet verified | The design does not depend on the answer: the ID is never persisted. |
| Q8 | Do the EDID vendor, model, and serial numbers come back non-zero? | Not yet verified for third-party monitors | `DisplayIdentity.hasStableHardwareIdentity` reports whether they did, the settings pane surfaces it per display, and `ordinalFallback` covers collisions. |
| Q9 | Are `kCGWindowBounds` and `kCGWindowOwnerName` available without Screen Recording permission? | **Verified, with a macOS 26 change** | The fields are available with no permission: a full window list with 261 entries and 33 distinct owner names came back on a machine that had never granted Screen Recording to the calling process. But the Dock's dock-level window is **excluded by `.excludeDesktopElements`** and is **not flagged on-screen**, so the strategy the plan described returns nothing on macOS 26. Two consequences: `SystemDockLocator` now queries `.optionAll` and filters on owner and layer, and the Dock's dock-level window bounds now span its entire display rather than hugging the bar, so they identify the host display but can no longer be used to measure geometry. |
| Q10 | Does an `LSUIElement` app with visible windows get App Napped? | Not yet verified | Idle CPU measured at 0.0% over two 20-second samples, which is consistent either way. Needs an Instruments energy run. |
| Q11 | Behaviour when the display hosting the Dock is disconnected | Not yet verified | Release-checklist item. Suppression is recomputed on every reconcile, so the expected behaviour is that the newly Dock-hosting display becomes the suppressed one. |
| Q12 | Cost of `NSWorkspace.icon(forFile:)` cold versus warm | Instrumented, not yet measured | `icon-rasterize` signposts wrap every rasterization, and all of it runs on the `IconProvider` actor, off the main actor. |

## Findings from comparing against the real Dock side by side

Captured with the real Dock and Dockyard's bar on the same display at `tilesize` 27:

- **Finder is a permanent tile, not a `persistent-apps` entry.** It is always the first tile and cannot be removed, exactly like the Trash. Dockyard synthesizes it from `/System/Library/CoreServices/Finder.app`, resolved through `TileEnvironment` so the tests stay hermetic and a machine where it cannot be resolved simply renders the rest.
- **The separator before the Trash region is always present,** not only when `persistent-others` is non-empty. The Trash always lives in that region, so the separator always has something after it.
- **Calendar and Clock icons come from dock tile plugins, not from the bundle icon.** The Dock renders them through each app's `NSDockTilePlugIn` loaded inside the Dock process: Calendar shows today's weekday and date, Clock shows a live analog face. `NSWorkspace.icon(forFile:)` returns the static bundle icon instead. Loading those plugins would mean loading third-party code into Dockyard, which needs `disable-library-validation` and is refused by the security posture.

  Calendar is reproduced by drawing over the bundle icon instead. The static icon's geometry was measured from its own pixels: the card occupies 80.47% of the canvas centred, the red band starts 1.46% below the card top and is 23.30% of the card's height, the band is `rgb(255, 62, 72)` and the body `rgb(236, 235, 236)`. `CalendarTileRenderer` repaints the body to cover the dot grid, then draws the localized weekday in the band and the day number in the body. The date is part of the icon cache key, and `NSCalendarDayChanged` triggers a refresh, so no timer is involved. Clock cannot be reproduced: a ticking second hand needs a timer, and timers are banned.

- **The Dock's own trash artwork is readable from its bundle.** `/System/Library/CoreServices/Dock.app/Contents/Resources/` contains `s-trashempty@2x.png` and `s-trashfull@2x.png`, which are pixel-identical to what the Dock renders. `NSImage(named: NSImage.trashEmptyName)` returns a much darker, older bin, and `NSWorkspace.icon(forFile:)` on `~/.Trash` returns a generic document icon. Dockyard reads the two PNGs with a fallback chain, since the file layout is undocumented and may change.

- **`~/.Trash` is TCC-protected: reading it needs Full Disk Access.** `FileManager.contentsOfDirectory` fails with "Operation not permitted", and so does `open(path, O_EVTONLY)`. Two consequences, both of which contradicted the plan:
  - The plan's emptiness check via `contentsOfDirectory` silently reported "empty" forever, so the Trash tile never showed its full state. `getattrlist` with `ATTR_DIR_ENTRYCOUNT` **does** work without Full Disk Access and returns the exact entry count, so that is what Dockyard uses. `stat` also succeeds, but `st_nlink` counts subdirectories rather than entries and is not a usable substitute.
  - A directory watcher on the Trash cannot be created at all, so the planned watcher was removed. The Trash state is instead recomputed on every snapshot rebuild, which costs one syscall and is triggered by the `NSWorkspace` notifications that already fire when Finder activates. In practice the tile updates as soon as the user interacts with Finder after changing the Trash.
- **Minimized windows appear as their own tiles in the real Dock** when `minimize-to-application` is false. They come from the window server rather than from preferences and cannot be enumerated without Accessibility, so Dockyard does not show them.
- **Magnification needs a ramp, and it can be had without a timer.** Snapping straight to the fully magnified layout on the first `mouseMoved` reads as abrupt next to the real Dock. Animating every update instead makes fast sweeps feel laggy. What matches: on entry, record a deadline 0.20 s out and animate each update over the *remaining* time, so the ramp decays to instant tracking on its own; on exit, animate the collapse over 0.16 s. Because AppKit suppresses implicit animations on a view's own backing layer but not on layers the app creates, the tile layers animate through the `CATransaction` while the blur view needs `NSAnimationContext` with `allowsImplicitAnimation`; running both inside one `NSAnimationContext` grouping keeps their timing identical.

- **A tracking area whose rect is recomputed on every `mouseMoved` breaks enter and exit bookkeeping.** The magnified state never collapsed because the tracking area was being removed and re-added inside the layout pass, and it was also the dominant cost per event, which made magnification feel sluggish. The tracking rect is now the panel's stable `bounds` and the interactive-rect test happens in the handler.
- **Programmatic cursor warps move the real Dock between displays** when they land inside the bottom trigger strip, and Dockyard's suppression follows correctly within the settle window. Warping back does not move it back: the Dock's own gesture needs real HID movement pressure against the edge.
- **Synthetic `rightMouseDown` events do not open the context menu** on a non-activating panel, though a real right-click does. Menu placement therefore has to be verified by hand.

## Other observations worth recording

- The primary display in Cocoa coordinates is the one containing the origin, and a secondary display placed to the left has a negative `frame.minX` while a display of a different height has a non-zero `frame.minY`. The test suite covers both arrangements because these are exactly the cases where a naive conversion puts a bar off-screen.
- A secondary display can report **no** `visibleFrame` inset at all, not even for the menu bar. The Dock-host test must therefore be an inset test on the Dock's own edge, not an assumption that every display reserves something.
- `/Applications/Safari.app` is a symlink into a cryptex on recent macOS, so resolving symlinks changes the launch path. That is desirable for validation but makes the check machine-dependent, so symlink resolution is injected through `TileEnvironment` and the tests stay hermetic.
- A manually added sublayer of a layer-backed `NSView`'s own layer is drawn **below** the layers of that view's subviews. The tiles were invisible behind the blur view until they were moved into a sibling view ordered above it.
